# VR performance investigation - October 31, 2026

A live render-thread bottleneck was found in Far Far West vtable validation. Repeated Windows memory queries for entries in the same memory region are now reused within a single validation call. No result survives that call; changed protection and unloaded memory are checked afresh. The optimization is restricted to the existing Far Far West UE 5.8.1/DX12 guard. Other games keep the original validator.

Two independent baseline thread snapshots found this validation in the render-thread Slate path. A matched rollback test measured 22.23 application FPS with the previous B88 backend and 31.44 FPS with the optimized 179 backend (41.5% improvement). A second optimized capture measured 31.44 FPS. These are real Meta telemetry application frame timestamps, not compositor refresh rate. See diagnostics/performance-20261031/live-results.json. Some diagnostic runs disabled controller input for desktop navigation; they are not controller acceptance tests. Final controls-enabled lobby captures measured 29.78 and 30.66 application FPS (p95 frame intervals 39.27 and 40.30 ms). The first final capture included a brief noninvasive thread-stack snapshot; the repeat did not. A temporary navigation-helper restoration issue was caught during testing, corrected, and verified true in the running game and saved configuration. The helper was removed.

The game remains below smooth VR performance in these stationary, off-head lobby tests. This is a confirmed bottleneck fix, not proof that the entire regression is resolved. Combat, worn-headset movement, transition borders and comfort require representative wearer testing. GPU readings alone did not establish a GPU limit.

The effects module also skips redundant brush/layout/transform work while transparent, and stops blank redraws after the fade-out transition. Visible effects retain their original artwork, animation state, redraw rate and full 1024x1024 texture. Native visibility and opacity are observed every tick; discovery cadence is unchanged. The class inventory API uses an indexed registry and was not proven to cause the slowdown.

The reticle module avoids repeated unchanged layout setters and allocations. Animated layout changes still propagate. The gun crosshair and hit X retain their separate 256x256 layer and existing v13 firing-camera ray. Empty-hand aim, crosshair depth/size, HUD/POI placement, controls and camera rules are unchanged.

No AA, resolution, graphics quality or stereo-rendering fallback was introduced. Native stereo and its existing split/warp fixes remain enabled. Temporary ASW, synchronization, GUI and controller test settings must be restored before handoff.

Validation: 90 profile tests and 33 native tests passed; backend and launcher builds passed. Memory-probe tests exhaust all 4096 executable-entry patterns, invalid addresses, query failures, memory region bounds, and fresh-call protection changes. A Windows API microbenchmark reduced validation time from 116426 ns to 8098 ns; this isolated result is not an FPS claim. The simulated transparent-effects harness reduced setters from 21600 to 12 and allocations from 14400 to zero while visible redraw count remained 300.

Evidence: diagnostics/performance-20261031/ contains frame captures, rollback results, thread stacks, benchmark, build/test logs, work-counts.json and final integrity.json.
